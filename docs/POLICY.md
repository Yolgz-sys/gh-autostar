# 自动点星的边界

这份文档记录一个不太舒服但必须说清楚的问题：**自动点星踩在灰色地带上**，
以及本项目为此做了哪些约束。

## 争议在哪

Star 是 GitHub 上唯一的"轻量认可"信号。它同时承担两个作用：
一是作者的情绪价值，二是推荐算法的输入。自动点星把"认可"这个动作
从人的即时决定变成了代码的副作用，于是产生两个风险：

1. **信号失真。** 如果一个工具被很多人装上，每次"用到"就自动点星，
   那这个仓库的星数增长里就混进了机器产生的部分。对看星数判断项目质量的人来说，
   这是噪音。
2. **账号风险。** GitHub 的[社区准则](https://docs.github.com/en/site-policy/github-terms/github-community-guidelines)
   对"虚假/自动化互动"有明确限制。单账号每天几颗星不会有事，
   但"高频 + 模式化 + 批量"是被重点识别的特征。

反过来，也有站得住脚的一面：**星是用户自己的账号、自己的认可**。
这个工具做的事情，本质上只是把"我用了你的东西，我想表示感谢"这个念头
从"懒得点"变成"自动完成"。它没有伪造身份，没有买星，没有刷量。

所以结论不是"能做/不能做"，而是**做成什么样才算合理**。

## 本项目的硬约束

| 约束 | 实现 | 为什么 |
|---|---|---|
| 每日上限 | `dailyCap`，默认 10 | 把量级压到"人类手动点星"的范围内 |
| 幂等 | 账本 + `GET /user/starred` 双重校验 | 同一个仓库永远只点一次，不会因为换 agent 重复点 |
| 触发收窄 | 只在 clone / 装依赖 / 读源码 / 采纳方案时触发 | 不扫 trending，不遍历搜索结果 |
| 黑名单优先 | `denylist` 在策略链最前面，`--force` 也绕不过 | 用户要有"永久拒绝"的权力 |
| 不点自己的仓库 | `skipOwnedByMe` 默认开启 | 自 star 是最典型的无意义信号污染 |
| 全量审计 | `ledger.jsonl` 记录 `starred` / `skipped` / `intended` / `failed` 及原因 | 用户随时能看清发生了什么，能一键撤销 |
| 可关闭 | `enabled: false` 或 `GH_AUTOSTAR_DISABLED=1` | 用户说不，就立刻停 |

## 分发建议

如果把本项目做成给别人用的插件：

- **默认 `mode: "dry-run"`**，让用户先看几天账本，自己决定是否放开。
  默认 `auto` 只适合"我自己给自己用"的场景。
- **明确告知**这是自动点星，而不是"装个 MCP 就能省事"。信息不对称下的自动行为
  才是不体面的那部分。
- **不要预置白名单**。把某个仓库塞进别人的默认配置里，性质就变了。

## 明确不该做的事

- 拿它给指定仓库刷星（那就不是"用到了才点"，而是定向刷量）；
- 改 `dailyCap` 到几百上千去跑批量；
- 用多个账号跑同一份配置；
- 在 `instructions` 里写"看到 GitHub 链接就点"，把触发条件放宽成"见到就点"。

代码没做技术上的硬阻止（开源工具挡不住有心人），但如果你要改这三处，
请先想清楚自己在做什么。

## 一句话

**它是"谢谢"的自动化，不是"数据"的自动化。** 两者的区别不在代码里，在触发条件里。
